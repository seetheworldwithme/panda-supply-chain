# Java → Go 原行为兼容实施计划

**Goal:** 旧前端仅替换后端地址后保持 Java 原业务行为，包括原有错误和副作用。
**Architecture:** 以七服务源码及原 JAR 为契约，在现有 Go 单体补齐业务，不修改 Java，不调整旧前端调用协议。外部传输用标准库并通过本机服务验证请求、签名、响应及数据库副作用；真实凭据和生产操作不进入测试。
**Tech Stack:** Go net/http、crypto、database/sql、testing；MySQL 本机 socket；现有 Python 对比工具。

1. 保存工作区基线，核查原行为与报告偏差。保留所有已有未提交内容；不提交、不推送、不部署。
2. 招行：完整读取 PaymentHelper/PaymentHttpHelper/PaymentUtil、Controller/Service/Mapper；先写本机 HTTP 签名与查询正向失败用例，执行红灯，再补真实签名传输、付款落库、确认/取消/退款与查询，保留原计数和错误分支。
3. 通联：核查 SM2 SDK 协议、交易同步、调度生命周期和已有替代实现；先写可执行失败用例，按原逻辑补实现。缺少外部配置与缺少实现分别记录。
4. 核查登录、导入、密码、短信、文件及网关协议的主动差异；按用户最新指令保留 Java 问题，不擅自修复。逐项先证实差异再调整。
5. 执行 Go 测试、vet、Python 测试与本机隔离写入验证；构建本次 Go 实例，核查前端实际请求和已有只读/写入对比。凭据与业务数据不输出。
6. 更新差异清单和真实存在的验收报告，分清行为一致、原系统错误、外部配置未验收和未实现，报告剩余边界。

验证入口：`cd backend && go test ./... -count=1 && go vet ./...`；本机写测试仅在 `PANDA_LOCAL_AUDIT=1` 时启用，使用独立 fixture 并清理。前端与真实外部成功链未验证时不声称全量可切换。
